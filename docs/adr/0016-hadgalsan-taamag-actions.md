# Хадгалсан таамгийг GitHub Actions өдөр бүр тооцож `forecast-log` branch-д commit хийнэ

(grill-ээр Майк шийдсэн, Claude нарийвчилсан, 2026-11-17.) ADR 0015-ын сэргээж тооцсон backtest нь "тэр өдөр юу гэж хэлсэн бэ"
гэдгийг нотлохгүй. Хадгалсан таамаг л нотолно, түүх нь эхэлсэн өдрөөсөө л бүрдэнэ. Тиймээс одооноос эхлүүлнэ. ADR 0008-ийн
"GitHub Actions cron байхгүй" гэсэн мөр нь **серверийн өгөгдлийн** тухай хэвээр: сервер өгөгдлөө өөрөө шинэчилсээр байна, энэ cron
зөвхөн log бичнэ.

## Шийдвэр

1. **Action өөрөө тооцно** (Render-ийг дуудаж хадгалахгүй). Ижил код (`src/live`, `src/serve`), ижил `app/model/`. Мөр бүрт:
   asof, model хувилбар (ADR 0015), 301 сэдэв × h1–h3 (Δ̂, pct, 80% интервал), asof өдөр тухайн сэдвийн мөр API-аас ирсэн эсэх (`was_missing`),
   ажилласан цаг, сангийн хувилбарууд.
2. **Render-тэй харьцуулалт (best-effort).** Action дараа нь Render-ийн `/api/trending`-ийг дуудна. Хариу ирээд **asof нь ижил** бол
   сэдэв бүрийн h1–h3 `pct` ба `y`-г (Render 5%-д тайрсан, уншилтыг бүхэлчилсэн тул Action-ийн тоог мөн адил хувиргаж) харьцуулж,
   зөрүүтэй сэдвийн тоо, хамгийн их зөрүүг бичнэ. Render унтсан, алдаа, asof өөр бол `skipped` + шалтгаан. Таамаг ямар ч үед хадгалагдана.
   Зөрүү гарвал код биш өгөгдлийн зөрүү (сэдвийн мөр Render татах үед хоцорсон) байж болно: `was_missing`-аар ялгана.
3. **Түүхий өгөгдөл: `main`-ийн `data/processed/` (суурь) + `forecast-log` дээрх өдөр тутмын жижиг delta.** Action дутуу өдрүүдийг
   Wikimedia-аас татаж (сервертэй ижил `update_cache`), шинэ өдрийн түүхий мөрүүдийг (≈ 301 + alias мөр, ~10 KB CSV) таамагтай хамт commit хийнэ.
   Дараагийн ажиллагаа суурь + бүх delta-аас эхэлнэ. Суурьтай давхцсан огнооны delta-г тоохгүй.
   - *Татгалзсан: parquet-ийг branch-д өдөр бүр дахин бичих.* Git нь binary-г бүтнээр нь хадгалдаг: ~1.7 MB × 365 ≈ 600 MB/жил.
   - *Татгалзсан: өдөр бүр бүх цонхыг Wikimedia-аас дахин татах.* Хурдны хувьд болно (сэдэв бүрт нэг хүсэлт хугацааг бүхэлд нь авна),
     гэхдээ хожим ирсэн, засварласан өгөгдөл орж ирэх тул "тэр өдөр бэлэн байсан өгөгдөл" давтагдахгүй, түүх Wikimedia-аас хамаарна.
     `actions/cache` ч бас тохирохгүй (7 хоног ашиглахгүй бол устдаг).
4. **Хоцролт.** asof нь үргэлж **Action ажиллаж буй UTC өдрийн өчигдөр**. D бэлэн эсэхийг сервертэй ижил дүрмээр шийднэ (`total_views` ≥ 28
   хоногийн медианы 50%, мөртэй сэдэв ≥ 50%). Бэлэн биш бол таамаг бичихгүй, `not_published` статус л бичнэ. 3 цагийн дараах хоёр дахь
   cron дахин оролдоно. Хоёулаа бүтэлгүй бол тэр өдөр **цоорхой** хэвээр: дараа нь нөхөж бичихгүй (D+1 мэдэгдсэний дараа бичвэл
   хадгалсан таамаг биш), (B)-ээр ч дүүргэхгүй.
5. **0 уншилт ба өгөгдөл байхгүй.** API 0 уншилттай өдрийг буцаадаггүй тул нэг сэдвийн түвшинд хоёрыг ялгах боломжгүй. D өдөр бэлэн
   гэж шийдсэний дараа мөргүй сэдвийг 0 гэж үзнэ (сургалттай ижил, `fill_days`). Ялгаж чадахгүй байгаагаа `was_missing`-аар бичнэ.
   Үр дүнг дүгнэх үед тэр сэдвийн D өдрийн мөр хожим ирсэн бол тэр таамгийг "өгөгдөл хоцорсон" гэж тэмдэглэж, оноонд оруулахгүй.
6. **Cron: 06:41 ба 09:41 UTC** (УБ 14:41, 17:41). Render 03:00 UTC-д шинэчилж, бүтэлгүй бол 06:00-д дахин оролддог (`src/live.py`).
   Харьцуулалт утгатай байхын тулд түүний дараа ажиллана. `:00`-оос зайлсхийсэн (GitHub-ийн ачаалал ихтэй үед run хоцордог).
   Wikimedia D өдрийг яг хэдэн цагт гаргадгийг бид хэмжээгүй: оролдлого бүрийн цаг, статусыг бичиж байгаад хожим тохируулна.
7. **`main` дээр commit хийхгүй**, зөвхөн `forecast-log` branch. Bot-ын өдөр тутмын commit PR workflow-той мөргөлдөхөөс сэргийлнэ.

8. **"Дутуу" нь хожим илэрсэн өдөр: устгахгүй, тэмдэг нэмнэ** (UI/UX grill, Майк сонгосон, 2026-11-17). Log нь зөвхөн нэмэгддэг.
   - Өдөр 4-р зүйлийн шалгуурыг давсан ч хожим дутуу байсан нь илэрч болно (хадгалах үед 65% бүрэн, Wikimedia хожим нөхсөн).
   - **Дахин шалгах:** Action бүр сүүлийн 7 өдрийн нийт уншилтыг дахин татна (англи Wikipedia-ийн нэгтгэл, нэг хүсэлт). Ингэснээр өдөр бүр D+1, D+3, D+7-д шалгагдана.
     Хадгалах үеийнхээс ≥ X% өссөн бол тэр өдөрт `incomplete_at_publish` тэмдэгтэй **тусдаа бичлэг** нэмнэ. Анхны бичлэгийг засахгүй.
     7 хоногийн цонх нь эхлэлийн утга: Wikimedia хэр удаан нөхдөгийг бид хэмжээгүй. Log ≥ 2 сар болсны дараа бодит засварын хугацаагаар дахин үзнэ.
   - **Хасах дүрэм:** D-ийн таамгийг D+3-ын бодит үр дүнтэй харьцуулдаг (сум, дүгнэлт h3-аас). **D эсвэл D+3** аль нэг нь `incomplete_at_publish` бол тэр таамаг оноонд орохгүй.
     Тиймээс D-ийн таамгийн оноо D+3-ын 7 хоногийн шалгалт дууссаны дараа (D+10) эцэслэгдэнэ.
   - **X%-ийг урьдчилж тогтооно:** track record-ын үр дүнг харахаас өмнө давтамжийн скриптээр (PLAN) тогтоож энд бичнэ. Өөрчлөх бүрд огноо ба шалтгааныг энд тэмдэглэнэ.
   - Хасагдсан өдрийг сэргээж тооцсон таамгаар нөхөхгүй (ADR 0015).
   - **Ил байдал:** track record хэдэн өдөр хасагдсаныг бичнэ ("3 өдрийг өгөгдөл дутуу байсан тул тооцоогүй →"). Дарахад "Найдвартай байдал" хуудсанд хасагдсан өдрүүдийн таамаг ба үр дүнгийн жагсаалт гарна.

## Хувилбарын pin

- Render: `python:3.13-slim` (minor-оор л тогтсон, patch хөвдөг) + `requirements-app.txt` (бүгд `==`, `catboost==1.2.10`).
- Action: `setup-python` 3.13 + **ижил** `requirements-app.txt`. `requirements.txt` (`>=`) ашиглахгүй.
- Model сургасан орчны CatBoost хувилбар `meta.json`-д бичигдээгүй. `tests/test_golden.py` нь `requirements-app.txt`-ийн орчинд
  `/api/*`-ийн хариуг шалгадаг тул Action-д мөн ажиллуулна. Сангийн хувилбарыг мөр бүрт бичдэг тул зөрүү гарвал харагдана.

## Эрсдэл

- Public repo 60 хоног идэвхгүй бол GitHub scheduled workflow-ийг унтраадаг. Bot-ын commit үүнийг тооцогдох эсэхийг шалгах. Цоорхой
  олон хоног үргэлжилбэл анзаарах арга хэрэгтэй.
