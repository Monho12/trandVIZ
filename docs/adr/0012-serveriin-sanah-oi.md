# Серверийн санах ойг ≤ 400 MiB: сүүлийн 366 өдөр, сэдвийн хэсгээр цэвэрлэх, heap-ийг буцаах

(Майкийн шийдвэр, 2026-11-10.) ADR 0011-ийн "нөөц бага" эрсдэлийг (512 MB-аас ~15–30 MiB зай) хаана.
Зорилго: оргил санах ой ≤ 400 MiB. **Үр дүн ЯГ ижил**: таамаг, `/api/*` хариу, `meta.json`, Загвар хуудасны тоо.
Model, `meta.json`, дизайн, цэвэрлэгээ/feature/scoring-ийн дүрэм өөрчлөгдөөгүй.

## Хэмжилт: эхлэх үед юу эзэлж байсан бэ (local, процессын RSS)

| Хэсэг | RSS | Тайлбар |
|---|---|---|
| Python + pandas/numpy | ~96 MiB | |
| catboost, fastapi, app import | ~55 MiB | |
| CatBoost-ийн 3 model (h1–h3) | ~71 MiB | `.cbm` файлууд 63 MiB |
| Түүхий cache (`RawCache`) | ~103 MiB | DataFrame нь 30 MiB (586k мөр); үлдсэн нь parquet уншсаны дараа pyarrow-ийн pool-д үлдсэн санах ой |
| `Snapshot.clean` (бүтэн, 590k мөр) | ~83 MiB | DataFrame 49 MiB (`article` 13, `category` 8, бусад 4.5 тус бүр), барих үед +20 оргил |
| `universe` (301 мөр × 38) | ~9 MiB | DataFrame 0.1 MiB; feature тооцох үеийн оргил +36 |
| `/api/model` (`pipeline`) | оргил +61 MiB | бүтэн 590k мөр дээр naive MAE (snapshot тутамд нэг удаа) |

Хамгийн их хувийг эзэлдэг нь бүтэн түүхийг (raw + clean) санах ойд байнга барих, мөн чөлөөлсөн ч процесст үлддэг heap.

## Шийдвэр

1. **Snapshot-д зөвхөн сүүлийн `KEEP_DAYS` = 366 өдөр.** Inference-ийн хамгийн урт цонх нь `level_365` (365 хоног + asof
   = `FEATURE_DAYS`). Бусад нь богино: `/api/topic`-ийн history 180, жагсаалт 30, "ердийн өдөр" 59, measurable 7.
   Нөөц хэрэггүй: цэвэрлэгээг (trim, spike нь бүтэн түүхээс хамаардаг) тайрахаас **өмнө** сэдэв бүрийн бүтэн түүхээр хийнэ.
   Тиймээс үлдсэн мөрүүд бүтэн хүснэгтийнхтэй index-ээрээ хүртэл ижил (`tests/test_server.py`).
2. **Цэвэрлэгээг сэдвийн хэсгүүдээр** (`serve.clean_chunks`, 40 сэдэв). `clean_frame`-ийн алхам бүр (alias, өдөр дүүргэх, trim,
   spike, анхаарал) сэдэв бүрээр бие даасан тул үр дүн нэг дор цэвэрлэсэнтэй ижил. Бүтэн 590k мөрийн хүснэгт хэзээ ч нэг дор үүсэхгүй.
3. **`/api/model`-ийн бүтэн түүхийн тоог** (`clean_rows`, эхлэх огноо, naive MAE, сэдвийн тоо) Snapshot барих үед хэсэг бүрээс
   нэмж тооцно (`evaluate.HistoryStats`). naive-ийн алдааг ижил дарааллаар залгаад дунджийг авдаг тул тоо ижил.
   Хүсэлт бүрт тооцохгүй.
4. **Түүхий cache-ийг санах ойд барихгүй.** Snapshot барьсны дараа чөлөөлнө. Шинэчлэлт өдөрт нэг удаа дискнээс уншина
   (`data/live/` эсвэл image-ийн `data/processed/`). Аль нь шинэ вэ гэдгийг `total_views`-ээр л харьцуулна,
   хоёр cache-ийг зэрэг бүтнээр нь уншихгүй.
5. **Heap-ийг OS-д буцаах:** Snapshot барьсны дараа `malloc_trim(0)`. Dockerfile-д `ARROW_DEFAULT_MEMORY_POOL=system`,
   `MALLOC_ARENA_MAX=2` нэмсэн. Эдгээр нь зөвхөн allocator-ын тохиргоо тул үр дүнд нөлөөлөхгүй.

**Хийгээгүй:** float64 → float32 (feature, таамаг өөрчлөгдөнө), `article` → category (тайрсан 110k мөрөнд ~2 MiB л
хэмнэнэ, эрэмбэ/groupby-ийн эрсдэлтэй).

cgroup-ийн тоонд page cache орсон тул хэмжилт бүрт ±50 MiB хэлбэлздэг (`main`-ийн эхлэх үе 373–469). Тиймээс хамгийн найдвартай
шалгуур нь хязгаарыг багасгаад OOM болох эсэх. VmHWM-д хуваалцсан `.so` хуудас орсон тул cgroup-ийнхаас их.
Шинэчлэлтийг wikimedia.org sandbox-оос хаалттай байсан тул ижил хэлбэрийн хуурамч API-аар хэмжсэн (ADR 0011-тэй адил).

нь оновчлолоос **өмнөх** кодоор бичсэн `tests/golden/api_sha256.json`-тэй ижил (data/processed, "өнөөдөр" = 2026-11-10).
Model, data/processed эсвэл scoring-ийг зориудаар өөрчилбөл `python tests/golden/make_golden.py`-аар шинэчилнэ.

## Эрсдэл

- Өгөгдөл өсөхөд Snapshot-ийн хэмжээ тогтмол (366 өдөр). Зөвхөн барих үеийн түүхий cache (~30 MiB, жилд ~110k мөр) өснө.
- Шинэчлэлт бүр дискнээс уншина (өдөрт нэг, хэдэн секунд). Render-ийн диск түр зуурынх тул дахин эхлэхэд `data/processed/`-ээс эхэлнэ (ADR 0011).
